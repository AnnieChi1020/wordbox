## 1. Architecture

```
┌──────────────── Browser (PWA) ────────────────┐
│  Next.js React Client Components              │
│  Web Speech API (pronunciation)               │
└──────────────┬────────────────────────────────┘
               │ Server Actions / Route Handlers
┌──────────────▼──────────── Vercel ────────────┐
│  Next.js (App Router) Server                  │
│   ├ lib/domain   pure functions: Leitner,     │
│   │              word selection, questions    │
│   ├ lib/ai       OpenAI calls + Zod checks    │
│   └ lib/db       Supabase server client       │
└───────┬───────────────────────────┬───────────┘
        │                           │
┌───────▼────────┐          ┌───────▼────────┐
│ Supabase       │          │ OpenAI API     │
│ Postgres + RLS │          │ structured out │
│ Auth (Google)  │          └────────────────┘
└────────────────┘
```

Principles:
- **Business logic lives in pure functions in `lib/domain`** (no database or network access), so the requirements' AC can be covered by unit tests.
- All writes go through Server Actions; the browser uses Supabase only for the sign-in flow and never writes tables directly.
- RLS is the last line of defense: even if server code has a bug, it cannot read other users' data.

## 4. Database

### 4.1 Schema

```sql
-- Phase 1 ---------------------------------------------------------------

  id uuid primary key references auth.users on delete cascade,

create type part_of_speech as enum (
  'noun','verb','adjective','adverb','pronoun',
  'preposition','conjunction','interjection','determiner','phrase'
);

create table words (
  id uuid primary key default gen_random_uuid(),
  user_id uuid not null references auth.users on delete cascade,
  text text not null,
  ipa text,
  is_important boolean not null default false,
  box smallint not null default 0 check (box between 0 and 5),
  next_due_on date not null,

create unique index words_user_text_uniq on words (user_id, lower(text));   -- R2.4
create index words_user_due_idx on words (user_id, next_due_on);
create index words_user_text_key_idx on words (user_id, text_key);
create index words_user_box_idx on words (user_id, box);

create table senses (
  id uuid primary key default gen_random_uuid(),
  word_id uuid not null references words on delete cascade,
  position smallint not null check (position between 1 and 3),
  pos part_of_speech not null,
  def_en text not null check (length(def_en) > 0),
  def_zh text not null check (length(def_zh) > 0),
  synonyms text[] not null default '{}' check (cardinality(synonyms) <= 5),
  antonyms text[] not null default '{}' check (cardinality(antonyms) <= 5),

    check (question_type in ('word_to_zh','word_to_synonym','word_to_antonym','zh_to_word')),
```

### 4.2 RLS

```sql
alter table profiles enable row level security;
create policy own on profiles using (id = auth.uid()) with check (id = auth.uid());

alter table words enable row level security;
create policy own on words using (user_id = auth.uid()) with check (user_id = auth.uid());

alter table senses enable row level security;
create policy own on senses
  using (exists (select 1 from words w where w.id = word_id and w.user_id = auth.uid()))
  with check (exists (select 1 from words w where w.id = word_id and w.user_id = auth.uid()));

-- review_logs, ai_generation_logs: user_id = auth.uid()
-- ai_distractors: checked through senses → words, written like the senses policy
```

### 4.3 Transactional RPCs

The Supabase JS client does not support multi-statement transactions, so multi-table writes are wrapped in Postgres functions (`security invoker`, subject to RLS):

| Function | Purpose | Behavior |
|---|---|---|
| `create_word(p_text, p_ipa, p_senses jsonb, p_today date)` | R2.7, R2.8 | Inserts the word and its senses; on a unique index conflict, returns the existing word id with `exists = true` |
| `update_word_content(p_word_id, p_ipa, p_senses jsonb)` | R4.3, R6.5 | For editing; updates in place. `p_senses` is in display order: entries with an `id` update that sense, entries without one are inserted, and senses not in the list are deleted; positions follow the array order. Senses whose content changed lose their ai_distractors; unchanged senses keep their cache and sense id. Updates `updated_at` |
| `replace_word_content(p_word_id, p_ipa, p_senses jsonb)` | R4.5 | For regeneration: deletes all old senses, inserts the new ones, and updates `updated_at`; the old senses' ai_distractors are deleted by cascade (R6.5) |
| `get_dashboard_stats(p_since date)` | R8.1, R8.2, R8.6 (Phase 3) | Read-only. Returns `{ total, by_box: number[6], daily: [{ date, count }] }`; `daily` holds the answer count per day for `local_date >= p_since` (only dates with answers). D17 |
| `apply_review(p_question_id, p_word_id, p_sense_id, p_question_type, p_is_correct, p_was_due, p_box_before, p_due_before, p_box_after, p_due_after, p_local_date)` | R7.3, R7.4 (Phase 2) | See below |

`apply_review` steps:
1. Lock the word (`for update`); if not found → `P0002`.
2. If `question_id` already exists → do nothing and return the existing log (`duplicate = true`).
3. If the word's current `box` and `next_due_on` differ from `p_box_before` and `p_due_before` → `40001` (D13).
4. Insert the review log, update the word's `box` and `next_due_on`, and return `{ is_correct, box_before, box_after, duplicate: false }`.

The Leitner rules are implemented only in `lib/domain/leitner.ts`; the RPC does not recompute them and only handles atomic writes and idempotency.

### 4.4 Profile creation

An insert trigger on `auth.users` creates the `profiles` row (timezone = `null`). After the sign-in callback, the client calls `initProfileTimezone(tz)` with `Intl.DateTimeFormat().resolvedOptions().timeZone`:

```sql
update profiles set timezone = $tz where id = auth.uid() and timezone is null;
```

- It writes only while `timezone is null` (R1.3) and is never updated automatically afterward.
- If the first write fails, the next sign-in tries again. Users who really are in UTC are initialized correctly too.
- The server checks that `tz` is a valid IANA time zone and skips the write otherwise.
- Reads compute local dates with `coalesce(timezone, 'UTC')` (§7.2).

## 5. AI design

### 5.1 Generating a word: output schema

OpenAI strict structured outputs require every field, so optional fields are represented with `null`.

```ts
const SenseSchema = z.object({
  pos: z.enum(POS_VALUES),
  def_en: z.string().min(1),
  def_zh: z.string().min(1),
  synonyms: z.array(z.string()).max(5),
  antonyms: z.array(z.string()).max(5),
  examples: z.array(z.string()).min(1).max(2),
});

const GenerateWordSchema = z.object({
  is_valid: z.boolean(),
  suggestions: z.array(z.string()).max(3),          // used when is_valid=false
  headword: z.string().nullable(),                  // dictionary headword spelling; null when is_valid=false
  ipa: z.string().nullable(),
  senses: z.array(SenseSchema).max(3),              // 1–3 when is_valid=true
});
```

After Zod validation, the server also checks that `senses.length ≥ 1` when `is_valid = true`; otherwise the response counts as an invalid format (R2.10).

### 5.2 Generating a word: prompt essentials

The system prompt (`lib/ai/prompts.ts`) must cover:
1. Role: writing dictionary entries for English learners in Taiwan.
2. Decide whether the input is a real English word or common phrase (including phrasal verbs and idioms); proper nouns, misspellings, and random strings are invalid, with up to 3 closest valid spellings as suggestions.
3. At most 3 senses, ordered from most to least common; different parts of speech of the same word are separate senses.
4. `def_en`: learner-friendly, at most 25 English words. `def_zh`: Traditional Chinese, Taiwan usage, at most 20 Chinese characters.
5. Synonyms and antonyms must match that sense: 0–5 each, single words or short phrases, never forced.
6. 1–2 examples of at most 20 English words, each containing the word.
7. `ipa`: American pronunciation wrapped in `/…/`; `null` when unsure.
8. Phrases use the part of speech `phrase`.
9. `headword`: the dictionary headword spelling. Normally lowercase; capitals are kept where English requires them (days, months, languages, nationalities, the pronoun I, abbreviations such as DNA). Only letter case may change, never spelling, inflection, or spacing.

The user's input goes only in the user message, explicitly labeled as 「要查詢的字」 (the word to look up), to guard against prompt injection.

### 5.3 Distractors (Phase 2)

```ts
const DistractorsSchema = z.object({ options: z.array(z.string()).length(3) });
```

Input: the question type, the prompt, the correct answer, and the quiz word's synonyms and antonyms. Requirements: same language, format, and part of speech as the correct answer; plausible but definitely wrong; never a synonym, and for `word_to_antonym` never an antonym either. The 3 returned options must be distinct, or the response counts as an invalid format. They are then merged with the candidates from the user's words and filtered by the R6.4 rules; if that still yields fewer than 3 distractors, generation counts as failed (R6.6).

How the cache is used (`lib/review/distractors.ts`):
- The AI always generates 3 and the cache stores 3. Questions use candidates from the user's words first and fill the rest, in order, from the cache (or the AI result).
- Cached options are filtered by R6.4 after reading too (the user's words or the sense may have changed); if too few remain, the AI is called again and the cache is overwritten.
- Nothing is cached when the AI fails.
- With `AI_MOCK=1`, the mock dispatches on the request `name`: distractor requests get recognizable options that satisfy R6.4, and the quiz word `mock distractor fail` returns a failure (to test R6.6).

### 5.4 Shared handling

- 20-second timeout (`AbortController`) with no automatic retry; the user retries manually (R2.10).
- Every call is logged to `ai_generation_logs` (R2.12).
- With `AI_MOCK=1`, data comes from `lib/ai/fixtures/*.json`. Fixtures must cover a valid word, a word with several senses (`run`), a phrase (`give up`), a misspelling (`aple`), a timeout, and an invalid format.

## 6. Server Actions

```ts
// lib/actions/words.ts
type AddWordResult =
  | { status: 'exists'; wordId: string }
  | { status: 'invalid'; suggestions: string[] }
  | { status: 'created'; wordId: string }
  | { status: 'error'; message: string };

addWord(input: string): Promise<AddWordResult>
  // 1. normalize + validate (R2.2, R2.3)
  // 2. look up lower(text) → exists (R2.4)
  // 3. generateWord → invalid / error
  // 4. canonicalText(input, headword) decides the stored spelling (R2.7, D12)
  // 5. create_word RPC (a unique index conflict under concurrency → exists)

updateWord(wordId, { ipa, senses }): Promise<Result>       // R4.3, R4.4; senses carry their existing ids → update_word_content
regenerateWord(wordId): Promise<Result>                    // R4.5, R4.6
deleteWord(wordId): Promise<Result>                        // R4.7
setImportant(wordId, value: boolean): Promise<Result>      // R3.5 (optimistic update in the UI)

// lib/actions/review.ts (Phase 2)
type Question = {
  questionId: string;              // crypto.randomUUID(), generated by the server
  wordId: string; senseId: string;
  type: QuestionType;
  prompt: string;                  // the word or the Chinese definition
  pos: PartOfSpeech;               // shown next to the prompt
  options: string[];               // 4, shuffled; which one is correct is not included (D15)
};

type AnswerResult =
  | { ok: true; isCorrect: boolean; correctOption: string; boxBefore: number; boxAfter: number }
  | { ok: false; message: string };

startReviewSession(): Promise<
  { ok: true; questions: Question[] } | { ok: false; message: string }
>                                           // questions = [] when the user has no words (R5.2)
submitAnswer({ questionId, wordId, senseId, questionType, options, selected }): Promise<AnswerResult>
  // the client sends questionId and options back unchanged; resubmissions are deduplicated by questionId (R7.3)
countDueWords(): Promise<number>            // ReviewIntro and the summary screen (R7.5)
```

### startReviewSession flow (R5, R6)

1. Read all words and senses (selection state + distractor candidates) and the profile time zone in one query.
2. `orderSessionCandidates` (§7.4) produces the full sequence; take the first 8.
3. For each word, pick a random sense and a random question type, and build the question from the user's words with `buildQuestion`.
4. Questions that return `needsAi` call `getDistractors` **in parallel** (D14).
5. A word that fails tries its other question types (each at most once); if all fail, the word is skipped and the next word in the sequence takes its place, going back to step 3, until there are 8 questions or the sequence runs out (R6.6).

### submitAnswer flow (R7.3, R7.4)

1. Validate the parameters: uuids, the question type, and `options` being 4 distinct strings that include `selected`.
2. Read the word, the sense (RLS limits this to the user's own), and the profile; if not found → `ok: false` (deleted or regenerated while answering, so the question does not count).
3. Find the correct option among `options` (rules below); if not exactly one → `ok: false`.
4. `applyAnswer` (§7.3) → `apply_review`; on `40001`, read again and retry once (D13).
5. On resubmission, `apply_review` returns the first log, so the result is the same.

Reads (list, popup, dashboard) query directly in Server Components. List filtering and sorting are driven by URL search params (R3.4) and run in the database.

### Word list pagination (NFR4, D11)

- Each query fetches 100 rows (`range`) and gets `count: exact` in the same query for the total; the sort ends with `id` so pages never repeat or skip rows.
- The first page is queried by the Server Component; scrolling to the bottom loads the next page with the `loadMoreWords(listQuery, offset)` action, and a 「載入更多」 (Load more) button provides the same for keyboard users.
- The server sends only compact data to the client list component, which renders each row, so RSC does not send the whole element tree.
- When filters, sort order, or data change, the server re-renders the first page and the client list resets; results from pages still loading are discarded.
- Performance is measured with `npm run test:perf` (production build, 2,000 words).

### Server-side answer checking in submitAnswer (R7.3)

The server keeps no session state. On each answer, it recomputes the correct option from the database (distractors exclude every synonym, and for `word_to_antonym` every antonym, so exactly one of the 4 options matches):
- `word_to_zh`: equals `sense.def_zh`
- `word_to_synonym`: is in `sense.synonyms` (case-insensitive)
- `word_to_antonym`: is in `sense.antonyms` (case-insensitive)
- `zh_to_word`: equals `word.text` (case-insensitive)

`isCorrect = selected === correctOption`.

`was_due` is also computed on the server from the local date at the time of answering, and then the `apply_review` RPC is called.

## 7. Domain logic (pure functions)

### 7.1 normalize.ts

### 7.2 dates.ts

```ts
localToday(timezone: string, now = new Date()): string   // 'YYYY-MM-DD'
addDays(date: string, n: number): string
```

Every "today" is computed by the server from `profiles.timezone` (`'UTC'` when null); the client's date is never trusted.

### 7.3 leitner.ts (R7.4)

```ts
const BASE_INTERVAL = [0, 1, 2, 4, 8, 16] as const;  // index = box

export function intervalDays(box: number, important: boolean): number {
  const d = BASE_INTERVAL[box];
  return important ? Math.max(1, Math.ceil(d / 2)) : d;
}

export function applyAnswer(
  s: { box: number; nextDueOn: string; isImportant: boolean },
  isCorrect: boolean,
  today: string,
): { box: number; nextDueOn: string; wasDue: boolean } {
  const wasDue = s.nextDueOn <= today;
  if (!isCorrect) return { box: 0, nextDueOn: addDays(today, 1), wasDue };
  if (!wasDue) return { box: s.box, nextDueOn: s.nextDueOn, wasDue };
  const box = Math.min(s.box + 1, 5);
  return { box, nextDueOn: addDays(today, intervalDays(box, s.isImportant)), wasDue };
}
```

### 7.4 selection.ts (R5.1)

```ts
orderSessionCandidates(words: WordState[], today: string, rng: Rng): WordState[]
  due    = words.filter(w => w.nextDueOn <= today)
             .sort(by nextDueOn asc, tie → rng)
  notDue = words.filter(w => w.nextDueOn > today)
             .sort(by box asc, then nextDueOn asc)
  return [...due, ...notDue]
```

It returns the full sequence rather than the first 8: `startReviewSession` builds questions from the first 8 in order, and when a word cannot get a question (R6.6) it continues down the same sequence.

### 7.5 questions.ts (R6)

```ts
type QuestionType = 'word_to_zh' | 'word_to_synonym' | 'word_to_antonym' | 'zh_to_word';

availableTypes(sense): QuestionType[]     // no word_to_synonym without synonyms; no word_to_antonym without antonyms

buildQuestion(target, sense, type, pool, rng):
  { question: Question } | { needsAi: QuestionDraft }
  // the caller picks the sense and type, and calls again with another type for R6.6
  // QuestionDraft: prompt, correct answer, partial candidates found in the user's words, missing, exclusion list

completeQuestion(draft, extra: string[], rng): Question | null
  // fills the gap with cached or AI options using the same exclusion list; null if still short (R6.6)

findCorrectOption(type, word, sense, options): string | null   // for checking answers in submitAnswer (§6)
```

Candidate sources and exclusion rules:

| Type | Candidate source (other words) | Additional exclusions |
|---|---|---|
| `word_to_zh` | Each sense's `def_zh` | Equal to the `def_zh` of any of the quiz word's senses |
| `word_to_synonym` | Each sense's `synonyms` | The quiz word itself and the synonyms of all its senses |
| `word_to_antonym` | Each sense's `antonyms` | The quiz word itself and the synonyms and antonyms of all its senses |
| `zh_to_word` | Each word's `text` | Words that are synonyms of the quiz word; words with any sense whose `def_zh` equals the prompt |

Shared rules: comparisons always trim and lowercase, duplicates are removed, and the correct answer is excluded. Ordering: candidates with the same part of speech come first, the rest in random order; take the first 3. If there are not enough, return `needsAi`; the action layer reads the `ai_distractors` cache and calls the AI only when there is no cache.

All randomness goes through the injected `rng`, so unit tests get reproducible results with a fixed seed.

### 7.6 heatmap.ts (R8.3, R8.4)

```ts
heatLevel(count: number): 0 | 1 | 2 | 3 | 4
  // 0 → 0, 1–8 → 1, 9–16 → 2, 17–32 → 3, 33+ → 4

heatmapStart(today: string): string
  // the first column's Sunday = 52 weeks before the Sunday of today's week; used as p_since for daily counts

type Cell = { date: string; count: number; level: 0 | 1 | 2 | 3 | 4 } | null

buildHeatmapGrid(counts: Map<string, number>, today: string): Cell[][]
  // 53 columns (weeks) × 7 rows (Sunday first); the last column contains today; cells after today are null (not shown)
```

Dates are always `YYYY-MM-DD` strings computed with `addDays` from §7.2, so time zones and daylight saving time do not affect them.

### 8.1 Dashboard (R8)

- **StatTotal**: the total number of words.
- **StarDistributionChart**: one horizontal bar per star count, 0–5 (CSS width percentage), each showing its count; `<dl>` or table semantics provide a text alternative.
- **Heatmap** (client component):
  - CSS Grid, 53 × 7; month labels on top, Sunday / Tuesday / Thursday / Saturday labels on the left; scrolls horizontally at phone widths, scrolled to the far right (most recent) by default.

  - R8.5: a tooltip such as 「2026 年 10 月 21 日：10 題」 (October 21, 2026: 10 answers) appears on hover on desktop and on tap on phones.
  - NFR5: roving tabindex, so the whole chart is a single Tab stop; arrow keys move between cells and the focused cell shows its tooltip. An sr-only summary reads 「過去一年共答 N 題，作答 M 天」 (N answers over M days in the past year).

### 8.2 PWA (R9)

- **Manifest** (`app/manifest.ts`): `name`, `short_name`, `start_url: "/words"`, `display: "standalone"`, `theme_color`, `background_color`, and icons at 192 / 512 plus a maskable 512. iOS home screen support comes from `apple-icon.png` and the `appleWebApp` metadata.
- **Service worker** (`public/sw.js`, hand-written, D19):
  - install: precache `/offline` and the icons.
  - fetch:
    - `/_next/static/*` and icons: cache-first (file names contain hashes, so they can be cached forever).
    - Page navigations (`request.mode === "navigate"`): network-only, falling back to the cached `/offline`.
    - Other requests (RSC, Server Actions, Supabase, APIs): not intercepted, always network (R9.2: cache static assets only).
  - activate: delete caches from old versions (cache names include a version number).
- **Registration**: `components/pwa/sw-register.tsx` is mounted in the layout and registers only in production (D20).
- **`proxy.ts`**: `/offline`, `/sw.js`, `/manifest.webmanifest`, and the icons need no sign-in.
- **Headers** (`next.config.ts`): `/sw.js` is served with `Cache-Control: no-cache, no-store, must-revalidate` so updates take effect immediately.
- **Testing**: `npm run test:pwa` runs Playwright against a production build (like `test:perf`) and checks the manifest, service worker registration, and the offline page on reload while offline.

### 8.4 Dark mode (R10)

**Switching** (D23, without next-themes)
- The setting is stored in `localStorage` as `theme`: `"light"` or `"dark"`; with no value (never switched manually), `prefers-color-scheme` at load time decides (R10.1).
- An inline script in the root layout's `<head>` adds or removes `.dark` on `<html>` and sets `color-scheme` before the first paint (R10.3). `<html>` has `suppressHydrationWarning`.
- `ThemeToggle` (`components/theme/theme-toggle.tsx`): a switch at the right of the top navigation bar, next to the sign-out button (`role="switch"`, `aria-checked`, labeled 「深色模式」 (Dark mode), on = dark; the icon next to it is a sun in light mode and a moon in dark mode). Switching writes `localStorage` and updates the class on `<html>`; the initial state reads whether `<html>` currently has `.dark`, avoiding hydration mismatches.
- System setting changes are not observed, and there is no "follow system" mode (R10.4).
- The login and offline pages have no navigation bar and no switch, but still apply the stored setting (R10 AC).

## 10. Testing strategy

- **Unit tests (Vitest)**: every function in `lib/domain/*`, using the requirements' AC directly as test cases (e.g. the 5 AC of R7.4 map to `leitner.test.ts`).
- **AI layer**: Zod validation and error branches tested with fixtures (valid, invalid, invalid format, timeout).
- **Database**: a local stack started with the Supabase CLI, testing RLS (user A cannot read user B's data) and the RPCs.
- **E2E (Playwright)**: `AI_MOCK=1` with local Supabase; sign-in injects a test session instead of going through Google.

## 11. Design decision log

| # | Decision | Rationale |
|---|---|---|
| D1 | Familiarity is tracked per word, not per sense | The list needs a single star count; conclusion of the Phase 1 discussion (Q5) |
| D2 | `next_due_on` is a date, not a timestamp | Leitner works in days; avoids edge cases from time zones and times of day |
| D3 | Filler words answered correctly are not promoted | Reviewing early would break the interval design (Q3) |
| D4 | The server rechecks answers and keeps no session | Stateless, suits serverless, and prevents tampering with results |
| D5 | review_logs are kept when a word is deleted (`set null`) | Dashboard history should not change when a word is deleted |
| D6 | Distractors come mainly from the user's words; the AI fills gaps and is cached | Lowers API cost (conclusion of the D2 discussion) |
| D7 | Online only; the PWA only provides installation | Offline sync is not worth the complexity (Q4) |
| D8 | No AI usage limit for now, but calls are logged | A limit can be added later directly from the logs (Q2) |
| D9 | Editing updates senses in place; only regeneration replaces them all | Editing invalidates the distractor cache only for changed senses (R6.5) and keeps `review_logs.sense_id` |
| D10 | `profiles.timezone` uses null for "not initialized" | Distinguishes "not initialized" from "user in UTC", and a failed first write can be retried |
| D11 | The word list loads 100 rows per page while scrolling | Rendering 2,000 words at once meant 1.6MB of RSC and 0.6–1s filtering; with pages it is about 6KB and 70–160ms, meeting NFR4. Also avoids PostgREST's default 1,000-row limit |
| D12 | Words are stored in their dictionary headword spelling, returned by the AI as `headword` in the same call | Always lowercasing would misspell Monday, English, I, and DNA; capitalizing the first letter does not follow dictionary convention. Only case differences are accepted, so the AI cannot silently change a word to its base form |
| D13 | `apply_review` uses box and next_due_on as an optimistic lock; on conflict the action rereads and retries once | Keeps a single TS implementation of the Leitner rules; answering the same word in two tabs at once cannot overwrite with stale state |
| D14 | Questions that need the AI are handled in parallel | With few words, every question may need the AI; calling sequentially could take 8 × 20 seconds in the worst case |
| D15 | Questions do not carry the correct answer; the client sends the 4 options back and the server checks the answer | Stateless and does not leak the answer; the server needs the options to return which one to mark green (R7.2) |
| D16 | A wrong answer sets box to 0 instead of standard Leitner's 1 | Stars = box, so setting 1 would give a new word an extra star for a wrong answer; the schedule is unchanged, and wrong words are still reviewed tomorrow |
| D17 | Dashboard stats are aggregated in the database by one read-only RPC | PostgREST cannot group by; one round trip gets the total, the star distribution, and daily answer counts, at most 371 rows |
| D18 | The bar chart and heatmap are built in CSS rather than with Recharts | With only 6 bars, a chart library would add about 100KB to the client bundle; a custom build also makes accessibility and dark mode easier to control |
| D19 | A hand-written service worker, without packages such as Serwist | Only static assets and the offline page need caching (R9.2), so the rules are few; avoids extra build configuration for Turbopack |
| D20 | The service worker registers only in production | Caching during development interferes with HMR; tested with `test:pwa` (production build) |
| D21 | ~~Brand colors are used only for icons, the PWA, and dashboard charts~~ (replaced by D22) | Colors provided by the user; the site theme stayed neutral to keep Phase 3's scope small |
| D22 | Brand colors extend to primary buttons, the navigation bar's selected state, and focus rings; the background stays white | The user asked for the brand colors to be applied; cream was tried as the page background but found unsuitable, so it went back to white |
| D23 | Dark mode uses a hand-written inline script and `localStorage`, without next-themes | The need is only a few options plus no flash; about 30 lines of custom code avoids a dependency and gives full control over when the script runs |
| D24 | In dark mode the primary color becomes a brand-300 light blue background with dark text | brand-900 lacks contrast on a dark background (2.93:1) |
| D25 | Antonym question distractors come only from other words' antonyms, and all antonyms of the quiz word's senses are excluded | Mirrors the synonym questions; excluding the antonyms of every sense guarantees exactly one of the 4 options matches (§6 checking). Synonyms are still excluded per R6.4: they would be clearly wrong answers, but a single rule is simpler |
